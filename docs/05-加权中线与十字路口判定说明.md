# 05 加权中线判定法 + 十字路口判定改造说明

> 改造对象：`Seekfree_TC264_Opensource_Library/code/{MIDLine_REMAIN.c/.h, Control_REMAIN.c/.h, SATA_MAIN.c}`
> 平台：TC264 双核 / MT9V03X 总钻风（188x120）/ 双电机差速 + 舵机
> 本文记录本轮全部代码改动、公式、状态机、屏显字段与调参方法。
> 改动后的源文件仍为 **GBK(936) + CRLF**，未新增 `.c`/`.h` 文件，`.cproject` 不用动。

---

## 0. 一句话总结

旧链路是「逆透视(IPM) → 俯视图找边 → 纯追踪 → 曲率 → 打角」，路口靠"强行回正"。
新链路是「逐行真实边界 → **按行加权求中线** → 互补滤波 → 偏差 → 分档打角」，路口用**五特征打分 + 状态机**判定，路口内**保持航向 + 限幅**而不是回正。

逆透视与纯追踪的源文件全部保留，`SATA_MAIN.c` 里 `#define SATA_PURSUIT_EN (0)` 一行就能切回旧方案做对照。

---

## 1. 为什么撤掉逆透视 + 纯追踪

| 旧方案的问题 | 加权中线的对策 |
| --- | --- |
| IPM 每帧 188x120 查表 + 俯视图 56x96 二次处理，主循环时间被吃掉 | 只多做一次逐行扫描（每行左右各走一遍），无查表、无浮点矩阵 |
| 俯视图分辨率被压缩，远端弯道只剩十来个像素，前瞻点抖动 | 权重直接作用在原图行上，远端信息不损失 |
| 纯追踪对前瞻距离/标定表极度敏感，标定表坏一帧就发散 | 只依赖行权重，没有需要标定的表 |
| 丢边线时俯视图直接没边可追 | 单侧边线 + 半宽推算，权重打 5 折继续输出 |

## 2. 加权中线判定法（`MIDLine_REMAIN.c`）

### 2.1 单行权重 `midline_weight(row, turn)`

`_u8/code/MIDLine_REMAIN.c:72`，双段式：

- **直道（turn = 0）**，`d = row`（row 大 = 靠车头）
  - `row < MIDLINE_WEIGHT_SEG_A_END(60)`：`w = row + 1`            —— 线性段
  - 否则：`w = (row-60)^2 / MIDLINE_WEIGHT_QUAD_DIV(4) + 61`     —— 二次段放大近景
  - 上限 `MIDLINE_WEIGHT_MAX(200)`，防止最近几行吃掉全部权重（"近景平台"）

- **弯道（turn = 1）**，权重方向翻转，让**远端主导**
  - `row > MIDLINE_TURN_HEIGHT(40)`：`w = MIDLINE_TURN_NEAR_W(8)` —— 近景只保留连续性
  - 否则：`w = (MT9V03X_H-1-row) + 1`                             —— 越远越大

- 最后统一乘行增益表：`w = w * mid_weight_list[row] / 100`
  `mid_weight_list[]` 默认全 100，想手工压掉某一行直接改（例如 `mid_weight_list[0] = 0` 让最远一行不参与）。

### 2.2 赛道上取中线（`Find_MIDLine`，`MIDLine_REMAIN.c:623`）

逐行（`row_start` → `row_end`，取左右基线行区间的交集）：

1. 左右两侧都有边界：`mid = (left + right) / 2`，同时按 `MIDLINE_WIDTH_LEARN_MIN/MAX`（0.70~1.40 倍）过滤掉被横臂带飞的行，参与赛道宽度学习；
2. 只有一侧：`mid = left + 半宽` 或 `right - 半宽`，`w *= MIDLINE_ONE_SIDE_SCALE(0.50)`；
3. 加权累加：`Σ(mid*w) / Σw` → `mid_line`；
4. 互补滤波：`center = 0.2*上帧 + 0.8*本次`（`MIDLINE_FILTER_OLD/NEW`）；
5. 置信度：`conf = 100 * Σw / Σw(full)`，满权重是"每行都两侧有效"的权重和；
6. `error = center - MT9V03X_W/2`（正 = 赛道偏右）。

有效行数 < `MIDLINE_MIN_ROWS(5)` 或 `Σw == 0` → 本帧失败（`valid = 0`），控制层沿用上一拍偏差。

## 3. 逐行真实边界扫描（`MIDLine_Row_Scan`，`MIDLine_REMAIN.c:116`）

十字判定的数据源，同时天然实现"过路口补线"：

1. 种子 = **上一帧** `mid_line_list[row]`（首帧取画面中心），种子落在黑点上就左右找最近白点；
2. 从种子向左/右走：
   - 遇到**薄黑条**（宽 ≤ `MIDLINE_RAW_MARK_MAX(10)` px）→ **跳过去继续走**（这就是路口两排横条不会切断边线的原因），一行最多跳 `MIDLINE_RAW_SKIP_MAX(6)` 段；
   - 遇到**厚黑块**（> 10 px）→ 认为到达赛道外的深色地板，取黑块靠近路面那一侧作为边界；
   - 一路全白 → 边界贴到图像左右沿（横臂张开时正是这个特征）；
3. 结果写 `raw_left[] / raw_right[]`，无效为 `MIDLINE_INVALID_COL`；
4. 顺带统计行区间 `18~78` 内落在路面内的短黑条根数，2~4 根/行记一次 `cross_mark_rows`（≥5 根是斑马线，交给 `Zebra_REMAIN`，这里**故意不认**）。

> 行区间 18~78 是刻意避开斑马线模块的 82~118 扫描带，两个模块不会互相误判。

## 4. 十字路口判定（`MIDLine_Cross_Score` + `MIDLine_Cross_Tick`）

### 4.1 五特征打分（最高 4 分，`MIDLINE_CROSS_SCORE_NEED = 3` 才认）

| 特征 | 判据 | 默认阈值 | 计分 |
| --- | --- | --- | --- |
| F1 宽行 | 该行 `(r - l) > 学习宽度 x 1.30` | ≥ `MIDLINE_CROSS_MIN_WIDE_ROWS(6)` 行 | +1 |
| F2 丢线带 | 左右**同时**无效连续 ≥ `GAP_MIN(3)` 行，取最长的一段 | — | 与 F4 联动 +1 |
| F4 断带上方 | 断带**更远处**仍有 ≥ `ABOVE_MIN(2)` 行完整边界 | — | F2 的闸门 |
| F3 外扩 | 相邻两行左边界继续左移 ≥ `RISE_D(6)` 且右边界继续右移 ≥ 6 | ≥ `RISE_MIN(4)` 次 | +1 |
| F5 短黑条 | 行区间 18~78 里有 2~4 根 ≤10px 短黑条的行数 | `MARK_MIN_ROWS(2)` ~ `MARK_MAX_ROWS(8)` | +1 |

- **F4 是 F2 的闸门**：断带上方还有线 = 路口（路面被横臂切断）；断带上方没线 = 出弯冲出去丢线，不算路口。
- **偏差闸门**：`|中线偏差| > MIDLINE_CROSS_TOL(34)` px 时本帧直接 `score = 0`，避免斜着入弯被误判成路口。

### 4.2 状态机

```
NONE ──score≥3──> CONFIRM ──连续 CONFIRM(2) 帧──> INSIDE ──(计时满 30 帧 且 连续 6 帧无特征)──> EXIT(6 帧) ──> COOLDOWN(20 帧) ──> NONE
                       └─ 掉分一帧 ─> NONE
```

| 状态 | 编号 | 行为 |
| --- | --- | --- |
| NONE | 0 | 正常加权中线 |
| CONFIRM | 1 | 正常加权中线，只累计命中帧数 |
| INSIDE | 2 | **锁存进路口前的中线（`cross_hold_center`）与中线快照（`cross_hold_line[]`）**，偏差冻结、宽度停止学习、缺线的行用快照补齐 |
| EXIT | 3 | 恢复正常中线，但**冻结宽度学习**（横臂刚消失时宽度还不可信） |
| COOLDOWN | 4 | 同上，防止二次误判 |

`MIDLine_Hold_Output()`（`MIDLine_REMAIN.c:557`）就是"保持航向"：
`error` 用锁存值 → 控制层看到的是一段稳定偏差 → 车顺着自己的航向穿过去，**绝不硬回正**。

## 5. 控制层配合（`Control_REMAIN.c`）

| 位置 | 改动 | 原因 |
| --- | --- | --- |
| `CONTROL_PURSUIT_EN` | 1 → **0** | 纯追踪撤出流水线，`Pursuit_Get()` 不再参与打角 |
| 打角 | `Servo_Set_Step(error * CONTROL_ERR_PX_TO_DEG, force_center)` | 偏差(px) → 角度 → 5 档舵机（460/440/474/418/500） |
| 路口 | `CONTROL_CROSS_FORCE_CENTER = 0`：需求**限幅**到 ±`CONTROL_CROSS_STEER_MAX_DEG` | 硬回中是"斜着进路口→冲角"的头号元凶，改成只允许小幅修正 |
| 路口 | `Servo_Clear_Hold()` | 别把出弯保持的旧打角带进路口 |
| 降速 | `slow = 1 - 0.0080*|error|`，下限 `CONTROL_CURVE_SLOW_MIN(0.45)` | 偏差越大弯越急，先降速再打角 |
| 置信度降速 | `conf < CONTROL_CONF_REF` 时按比例再乘，下限 `CONTROL_CONF_SLOW_MIN` | `conf` 掉了说明中线不可信，先看清再走 |
| 路口 | `slow *= CONTROL_CROSS_SPEED_SCALE(0.80)`、`ratio *= CONTROL_CROSS_DIFF_SCALE` | 横臂外侧线不可信，路口最怕车身横摆 |
| 差速 | `ratio = CONTROL_DIFF_K * error`，限幅 `CONTROL_DIFF_K_MAX` | 偏差为正（赛道偏右）→ 左轮快 |

打角限幅 `CONTROL_CROSS_STEER_MAX_DEG` 默认 **2.80°**（只允许 452/468 两个微调档，配合 `CONTROL_ERR_PX_TO_DEG = 0.45` 就是"偏差 6 px 打满"）：能修正航向、又不会把前轮打死。现场按 2.0 ~ 4.0 之间收。

## 9. 第二轮：路口专用加权中线优化（解决"路口一拐弯就离道"）

实车现象：**走到十字路口，车会自己拐弯，直接离开原定路线。** 根因有三个，都在"路口这一段没有任何横向信息，算法却在硬凑一个"：

| 根因 | 现象 | 修法 |
| --- | --- | --- |
| 权重方向错 | 常规加权是"近景权重大"，但路口近景全是**横臂的白色开口**，`(左边界+右边界)/2` 恒等于画面中心、远端跟着横臂一起张开 → 中线**恒定指向横臂方向** | 路口区（`cross_hint = 1`）权重翻转成远端主导：`MIDLINE_CROSS_FAR_EN`，只信"远端还连着主路"的那些行 |
| 宽行不该参与 | 一行宽度 > 学习宽度 ×1.30 就是横臂开口，这行的"中点"由开口决定、不由赛道决定 | 路口区直接丢弃（`MIDLINE_CROSS_NEAR_OFF_EN`），平常区权重打 2 折（`MIDLINE_WIDE_SCALE`），保留连续性 |
| 丢线后还在打舵 | 路口正中看不到任何边线时，老代码 `error = control_last_error`，等于**一直按同一个角打舵**，车必然沿一段圆弧拐出赛道 | ① `MIDLine_Lost_Output()` / `MIDLine_Cross_Output(…, 0)` 让偏差**每帧指数回中**；② `Control_Tick` 里丢线改成 `error = control_last_error * CONTROL_LOST_DECAY` |

### 9.1 关键时序：路口策略必须早一帧生效

打分要等中线算完才出来，等它出来这一帧的中线已经被横臂拉偏、舵机已经打错角了。所以 `Find_MIDLine()` 开头先算 `cross_hint`：

```c
cross_hint = (状态既不是 NONE 也不是 COOLDOWN) || (上一帧 cross_score >= MIDLINE_CROSS_HINT_SCORE);
```

本帧的权重翻转和宽行丢弃全部按 `cross_hint` 走，等价于**零延迟**。

### 9.2 路口内输出改成"回中"而不是"保持"

`MIDLine_Cross_Output(center_now, has_line)`（`MIDLine_REMAIN.c`）：

- `has_line = 1`（远端还连着主路）→ 直接输出远端主导算出来的中线，车头自然回正；
- `has_line = 0`（画面里只剩白色开口）→ `target = center + (中心 - center) * MIDLINE_CROSS_DECAY`，偏差每帧往中心收 22%，约 10 帧（0.2 s）就基本回正，**穿过路口走的是直线不是圆弧**。

> 老注释里写的"保持进路口前的航向"正是问题本身：保持 = 恒角打舵 = 圆弧。

### 9.3 配套的四个保护

| 保护 | 宏 | 作用 |
| --- | --- | --- |
| 单侧贴边判无效 | `MIDLINE_EDGE_INVALID_EN` / `MIDLINE_EDGE_MARGIN(2)` | 边界已经贴到画面边缘 = 外侧地板被横臂吃进画面，这行推出来的中点完全失真 |
| 中线单帧跳变限幅 | `MIDLINE_MAX_JUMP_PX(20)` | 横臂进场那一帧中线可能跳几十像素，舵机会抽一下 |
| 丢线回中 | `MIDLINE_LOST_DECAY(0.35)` / `CONTROL_LOST_DECAY(0.85)` | 看不见赛道时最安全的方向是回正 |
| 路口打角上限放宽 | `CONTROL_CROSS_STEER_MAX_DEG` 2.8 → **4.5** | 2.8° 太小，路口里纠不回来，带着偏差一路开出赛道 |

### 9.4 这一轮新增的调参

| 症状 | 改哪里 |
| --- | --- |
| 路口里还是有点往外偏 | `MIDLINE_CROSS_DECAY` 调大（0.22 → 0.35，回中更快） |
| 路口里回中太急、车头点头 | `MIDLINE_CROSS_DECAY` 调小，`MIDLINE_MAX_JUMP_PX` 调小 |
| 路口内纠偏不够 | `CONTROL_CROSS_STEER_MAX_DEG` 加大到 5.5~6.0 |
| 路口误判成弯道 | `MIDLINE_CROSS_HINT_SCORE` 提到 3（只在真命中时才切路口策略） |
| 过弯时宽行被误丢 | `MIDLINE_CROSS_WIDTH_RATIO` 提到 1.45 |

## 10. 第三轮：四个直角连线补基线（把补出来的线直接当基线用）

第二轮解决的是"别被横臂带跑"，只要路口里还能看到远端主路就够用。但**车头压进路口中央**的时候，远景常常只剩一片白，远端主导也失效了 —— 这时唯一还连着物理结构的东西，就是横臂两侧的**四个直角**。第三轮就围绕这四个点做文章。

### 10.1 几何：四个角点定两条线

```
        row 小（远）
   对面左直角 ●━━━━━━━━━━━━● 对面右直角      ← far_row：横臂远端外面那一行
               ┃  横臂（白） ┃
    近处左直角 ●━━━━━━━━━━━━● 近处右直角      ← near_row：横臂近端外面那一行
        row 大（近）
```

- **近处两个直角** = 横臂近端外面那一行的左右边界；
- **对面两个直角** = 横臂远端外面那一行的左右边界；
- 连线规则固定为**左连左、右连右**（`col = k * row + b`，两点定一条直线），永远不允许左右交叉；
- 区间 `[far_row, near_row]` 里横臂把左右边界推到了画面两侧，那个位置**本来就没有物理意义**，所以这段区间内的行边界直接用连线值替换，补出来的两条线再取中点 = 路口内的中线。

### 10.2 判据：怎么才算"四个直角都对上了"

| 步骤 | 判据 | 宏 |
| --- | --- | --- |
| 1. 找横臂 | 两侧都有数据的行里，宽度 > 学习宽度 ×1.35 | `MIDLINE_CORNER_WIDE_RATIO(1.35)` |
| 2. 选横臂段 | 从车头往远处扫，取**最靠车头**的一段连续横臂行（允许断 2 行抗噪），长度 3~72 行 | `MIDLINE_CORNER_MIN_LEN/MAX_LEN/HOLE` |
| 3. 近端必须看得见 | 横臂最近端不能压到 `MT9V03X_H-6` 以内，否则近处两个角已经出画面 | `MIDLINE_CORNER_NEAR_BOT` |
| 4. 近处是"两个角"不是"一条边" | 近端外面那一行的宽度要回到学习宽度的 0.60~1.50 倍，**并且左右边界同时向外跳 ≥ 5 px** | `MIDLINE_CORNER_WIDTH_MIN/MAX`、`MIDLINE_CORNER_JUMP_MIN(5)` |
| 5. 对面同理 | 远端外面那一行的宽度也要在 0.60~1.50 倍之间；看不到就退到"用近端基线斜率外推" | `MIDLINE_CORNER_FALLBACK_EN`、`MIDLINE_CORNER_FAR_TOP(4)` |
| 6. 连线要合法 | 斜率 `\|k\| ≤ 2.5`；区间内逐行验算：左右都在画面里、左列 < 右列 | `MIDLINE_CORNER_K_MAX(2.50)` |
| 7. 防抖 | 连续 2 帧成立才算成立；此后基线保持 0.5s（第 14 节） | `MIDLINE_CORNER_CONFIRM(2)`、`MIDLINE_CORNER_HOLD_MS(500)` |

任何一条不满足就**整段放弃**（`corner_ready = 0`），退回第二轮的纯特征打分 —— 宁可不补，也不半补、不补错。

### 10.3 补线怎么参与加权（为什么"对巡线要求高"）

补出来的行不是真实测量，所以：

1. 行循环里，补线区间内的左右边界被连线覆盖，该行权重乘 `MIDLINE_CORNER_WEIGHT(0.85)` 打折，**满权重 `w_fun` 不打折** → 置信度自动下降，控制层降速降增益；
2. 直角对成立时 `cross_hint = 1`，路口策略**本帧立刻生效**（不等打分、不等状态机）；
3. 四个直角是比"数特征"更硬的证据：`Find_MIDLine` 里直接 `score = max(score, MIDLINE_CROSS_SCORE_NEED)` 保底，两帧内进 `INSIDE`；
4. **两条基线全断的兜底**：车正压路口中央时 `!bedline_left.valid && !bedline_right.valid` 直接 return 的老路径，现在先用 `MIDLine_Corner_Center()` 拿两条连线自己加权算中线、`MIDLine_Corner_Fill()` 写满 `midline_info.line[]` —— 不需要基线也能出中线；
5. 路口里上一帧的中线可能被横臂带偏，`MIDLine_Row_Scan` 加了一条：只在路口（`cross_hint = 1`）且种子跑到画面两侧 1/4 以外时，把种子拉回画面中路，从中间往两边扫。

## 13. 弯道降速收窄 10%

第 12 节把整体速度抬了一倍之后，原来那条"偏差越大降得越狠"的曲线跟着放大，弯里降到 `0.45 → 0.495` 就感觉拖不动了。这一节只动**弯道这一项**降速，路口/丢线/置信度三项降速的比例一律不碰。

新增一个增益放在原曲线**算完之后、夹 1.0 之前**：

```c
slow = 1.0f - (CONTROL_CURVE_SLOW_K * abs_err);
if(slow < CONTROL_CURVE_SLOW_MIN) slow = CONTROL_CURVE_SLOW_MIN;

slow = slow * CONTROL_CURVE_SLOW_GAIN;      // 1.10
if(slow > 1.0f) slow = 1.0f;                // 直道夹回 1.0，不会比基础速度更快
```

- 只抬"被降掉的那部分"，等效于**弯道速度 ×1.10**；直道 `slow` 本来就是 1.0，乘完夹回去，速度一点没变。
- `CONTROL_CURVE_SLOW_MIN` 仍是 0.45（表示"最深降到基础的 45%"这个设计意图不变），实际生效下限变成 `0.45 × 1.10 = 0.495`。

| 20 | 0.84 | 126.0 | 0.924 | 138.6 | +10% |
| 40 | 0.68 | 102.0 | 0.748 | 112.2 | +10% |
| 60 | 0.52 | 78.0 | 0.572 | 85.8 | +10% |

## 14. 直角基线保持 0.5 秒（把补线真正用起来）

第 10 节的补线只在 `[far_row, near_row]` 这一段里生效，横臂一翻过去、车一开进路口中央，基线就没了——那时候只剩"丢线 → 按 `MIDLINE_CROSS_DECAY` 回中"这一套，本质还是常量角，**路口里想往哪拐全看运气**。这一节把"连成的基线"变成有时效的状态量：

```
近处两个直角 + 对面两个直角 都对上
        │ 连续 2 帧（只有近处两个直角要 5 帧）
        ▼
   corner_ready = 1 ── 基线投入行循环
        │
        ├── 还在看得到拐角 → corner_keep 每帧续满 25（0.5s）、corner_slide 归零
        │
        └── 看不到拐角   → corner_keep 每帧 -1，corner_slide 每帧 +1（基线随车往车头滑）
                              keep 归零 → 释放基线，退回第二轮的回中式输出
        │
        └── corner_run 超过 50 帧（1s）→ 强制释放（车卡在路口里也不会一直挂基线）
```

### 14.1 七处改动

| # | 项目 | 改前 | 改后 |
| --- | --- | --- | --- |
| 1 | 保持时长 | `MIDLINE_CORNER_KEEP(12)` = 240 ms | `MIDLINE_CORNER_HOLD_MS(500)` → `MIDLINE_CORNER_KEEP = 500/20 = 25` 帧 |
| 2 | 补线行区间 | 只补 `[far_row, near_row]`（横臂带） | 横臂带 **+ 近端直角以下一直到画面底部**（`MIDLINE_CORNER_FILL_LOW_EN`）——那一段正是路口中央，本来就没有真实边线 |
| 3 | 保持期基线漂移 | 冻结在最近一次检测的位置 | 每帧往下平移 `MIDLINE_CORNER_SLIDE_PX(1)` 行，查线用 `row - slide` |
| 4 | 确认门槛 | 一律 2 帧，且只有"四个直角"能确认 | 四个直角 2 帧；只有近处两个直角 5 帧（`MIDLINE_CORNER_CONFIRM_NEAR`，几何靠外推，要更保守） |
| 5 | 补线总时长 | 无上限 | `MIDLINE_CORNER_RUN_MAX(50)` 帧 = 1 s |
| 6 | 单侧可用性 | 哪侧连线算得出来就覆盖哪侧 | **两条连线必须都在、且左列 < 右列**，否则本行不补（避免"半条基线"把中线拉歪） |
| 7 | 真实边线优先级 | 横臂带内无条件覆盖 | 横臂带内无条件覆盖；**近端以下只在真实边线断了（任一侧无效）时才补**，真实边线永远优先 |

### 14.2 两个关键实现点

1. **识别失败不能冲掉上一帧的基线**。`MIDLine_Corner_Detect_One()` 一进来就把 `corner_left/right` 的 `valid` 清 0，如果保持期里某一帧没识别到，上一帧的连线就没了。所以外面套了一层 `MIDLine_Corner_Detect()`：先备份 `bak_l/bak_r`，调用完若 `corner_state_now == 0` 就原样还原——"保持 0.5s"靠的就是这份备份。
2. **基线要跟着车走**。车在动，画面里的拐角每帧往车头方向挪。`corner_slide` 数着"丢了多久没看到拐角"，行循环里用 `r_line = row - corner_slide * SLIDE_PX` 去查线，等效于把整条基线往画面下方平移。`SLIDE_PX=1` 是按基础速度 150（≈250 mm/s、图像 80 行 ≈ 0.4 m 视野）估的，太快就调到 2。

`MIDLine_Corner_Range()` 是新增的公共行区间计算：两条兜底路径（`MIDLine_Corner_Center` / `MIDLine_Corner_Fill`，即两侧基线全断、车正压路口中央时）也用同一套区间和漂移，保证"行循环补的"和"兜底算中线的"用的是同一条基线。

## 15. 逐行继承补线（解决路口"丢线"）

### 15.1 丢线是什么、为什么会毁掉中线

`MIDLine_Row_Scan()` 对每一行独立地"从种子往两边走，撞到厚黑块才算边界"。撞不到（整行白、种子落在黑块上、薄黑条连着超过 6 根）那一行就直接 `continue`，`raw_left/raw_right` 留成 `MIDLINE_INVALID_COL`。路口里这种事成片出现：

- 横臂近沿那几行，左右两条边线的**中间**是白开口，从种子往外走会一路走到画面边缘；
- 深色地板被横臂"吃"进画面之后，某些行的边界完全落在镜头外；
- 偶尔会出现左边界跑到了右边界右边（左右交叉）。

断口一旦超过 `MIDLINE_MIN_ROWS` 行，整帧就掉进丢线分支；断口在 1~8 行时更阴——中线在断口上下两段之间跳变，加权和偏。

### 15.2 参考做法 vs 本工程的做法

参考代码的思路是：找一个已经算好的种子行，从它往上逐行走，每行在上一行列号附近开窗口找跳变；**找不到就继承上一行，左右交叉就整行继承**。

本工程照这个骨架做，但补了五点，因为"整行继承"在路口里会留下台阶：

| # | 参考做法 | 本工程做法 | 为什么 |
| --- | --- | --- | --- |
| 1 | 从种子行往上扫 | **从车头那侧（row 大）往远端（row 小）逐行、无跳** | 近处边界最可信，继承必须由近及远，否则远处一个假边界会把整条线带歪 |
| 2 | 找不到 → 沿用上一行列号 | 先用**上次有效宽度**补那一侧（`nl = r - width` / `nr = l + width`）；宽度超过 学习宽度×1.6 说明那几行是横臂张开，改走**斜率外推** | 保宽度补出来的是一条平行线，台阶感最小；横臂行的宽度本身不可信，只能靠斜率 |
| 3 | 左右交叉 → 整行继承 | 左右交叉 / 两侧都丢 → 用**最近两行真实边界的步进**做斜率外推，单行步进夹在 ±`MIDLINE_FILL_STEP_MAX(3)` px | 死跟上一行在路口里会拐成直角，斜率外推才是"往前接" |
| 4 | 补出来的行与真实行同权 | 补出来的行权重乘 **`MIDLINE_FILL_WEIGHT(70)%`** | 真实边线永远压得住补线，补线只是"不让它断" |
| 5 | 无上限 | 连续补 **≤ `MIDLINE_FILL_MAX_ROWS(16)`** 行；外推出画面或交叉立刻停手 | 再往上的行就是纯粹编造，宁可空着交给回中式输出 |

### 15.3 三个必须守住的顺序

顺手把这三个顺序固化了，改代码时不要动：

1. **补线在直角对识别之后**（`MIDLine_Row_Scan()` → `MIDLine_Corner_Detect()` → `MIDLine_Edge_Fill()` → 行循环）。直角对靠"真断带"找拐点，先补线就再也找不到断带，`corner_state` 会一直 0。
2. **补线在行循环之前**。这一帧的加权就要用补好的边界，否则补了个寂寞。
3. **路口特征打分只认补线前的真实边界**。`MIDLine_Edge_Fill()` 一进来先把 `raw_left/raw_right` 拷进 `real_left/real_right`，`MIDLine_Cross_Score()` 的 F1 宽行 / F2 丢线带 / F3 外扩全部改用这一份。**否则补线会把"丢线带"特征抹平，路口永远判不出来**——这是这一轮最容易踩的坑。

### 15.4 屏显

`y=144` 新增一行：`L` + 本帧补出来的行数（`midline_info.fill_use`）。末行 `144+15 = 159 < 160`，刚好放得下。

## 16. 第六轮：为什么"有的路口过了、有的路口还是拐"（四道闸）

现象：同一套参数下，一部分十字路口直着过去，另一部分还是往横臂方向拐。

拆开看是四个各自独立的漏洞，本轮各补一道闸。

### 16.1 闸一：路口内不再"跟着新算出来的中线走"

老逻辑在 INSIDE 里是 `MIDLine_Cross_Output(center_now, 1)`——只要本帧还有一行可信行，就直接采用本帧算出来的中线。问题是路口里"算出来的中线"本身就不可信：远端行可能落在**对面那条横穿的赛道**上、直角补线的斜率误差也在这时候最大。中线一偏，车就跟着偏。

现在改成"只给很小的修正权限"：

```c
float dev = center_now - cross_hold_snap;              // 相对"进路口那一帧的中线"
dev = clamp(dev, ±MIDLINE_CROSS_TRUST_PX);             // 默认 ±8 px
target = cross_hold_snap + dev;
```

`cross_hold_snap` 只在 CONFIRM→INSIDE 那一帧写一次，之后不再动。于是路口内航向**最多被修正 8 px**，横臂开口、对面路口错位、补线斜率误差都会被这一道闸挡住。

### 16.2 闸二：路口"快速通道"（不等五特征打分）

五特征要"连成片"才成立，边线断得不干净的窄臂路口会漏判——而漏判的那几帧正是开口把中线往外拽的时候。所以加一条纯几何的快速通道：

```c
l_near = bedline_left.k  * row_start + bedline_left.b;   // 近端行左右基线列号
r_near = bedline_right.k * row_start + bedline_right.b;
if((r_near - l_near) > width_ref * MIDLINE_CROSS_OPEN_RATIO) { open_now = 1; }   // 1.45 倍
```

- 触发当帧就把 `cross_hint` 拉高（远端主导 + 丢弃宽行）；
- 连续 `MIDLINE_CROSS_OPEN_FRAMES`（3 帧）成立，直接按"命中"喂给状态机，**绕过 `MIDLINE_CROSS_TOL` 的居中门控**（斜着进路口的时候反而最需要航向锁）；
- 断续的宽不算（`cross_open_cnt` 清零），避免一条粗黑线把宽度顶一下就误进路口。

赛道本身宽度是恒定的，弯道不会让"近端行宽度"涨到 1.45 倍，所以这条通道不会误伤弯道。

### 16.3 闸三：跨帧限幅在路口帧收到 8 px

原来的单帧限幅是 `MIDLINE_MAX_JUMP_PX = 20`，对路口来说太宽松——开口一帧把中线拽 30 px，限幅后还剩 20 px 落到输出上。

```c
float jump_lim = (1 == cross_hint) ? (MIDLINE_CROSS_TRUST_PX) : (MIDLINE_MAX_JUMP_PX);
```

这一条覆盖了 `cross_hint` 一旦为真、但状态机还没进 INSIDE 的那 3~5 帧（闸一管不到的空窗）。

### 16.4 闸四：路口帧里，继承补出来的行一条都不用

`MIDLine_Edge_Fill()` 是拿近处边线按"上次斜率"往上顶，误差随行数放大：`MIDLINE_FILL_MAX_ROWS(16) × MIDLINE_FILL_STEP_MAX(3) = 48 px`。而路口恰恰是边线断得最多的地方——补线越活跃，中线越歪。

```c
if(1 == fill_flag[row])
{
    if(1 == cross_hint) { continue; }        // 路口帧：这一行直接不参与加权
    w_row = w_row * MIDLINE_FILL_WEIGHT / 100;
}
```

路口内的正确答案是"保持进路口那一刻的航向"，不是"把补出来的线当中线"。丢行丢到 `num < MIDLINE_MIN_ROWS` 时，正好落到已有的 `MIDLine_Cross_Output(cross_hold_center, 0)` 分支——指数回中，走直线穿过去。

### 16.5 附带：出路口立刻放掉直角基线

`INSIDE → EXIT` 转移时清零 `corner_keep / corner_ready / corner_slide`。路口已经过去，再挂着补线会把"出路口第一帧"的中线按路口几何算歪，而那一帧正是控制环最敏感的时刻。

### 16.6 这一轮新增的调参

| 宏 | 默认 | 作用 |
| --- | --- | --- |
| `MIDLINE_CROSS_TRUST_PX` | `8.0f` | 路口内允许的修正量。车在路口里还是被拽偏 → 降到 5；路口内有真实的轻微弯却过不去 → 提到 12 |
| `MIDLINE_CROSS_OPEN_RATIO` | `1.45f` | 快速通道的宽度倍数。路口判不出来 → 降到 1.35；弯道被误判成路口 → 提到 1.55 |
| `MIDLINE_CROSS_OPEN_FRAMES` | `3` | 快速通道要连续几帧。想让进路口更快 → 2；想更保守 → 5 |
| `MIDLINE_CROSS_OPEN_EN` | `1` | 整条快速通道的开关 |

## 17. 第七轮：直角弯判界外（直角弯不转向）

### 17.1 现象与几何本质

直角弯（丁字口的单侧支路、赛道本身的直角拐角）和十字路口的区别：**十字路口是两侧同时张开，直角弯只有一侧张开**。

直角张开的那一侧，从车头往那边看过去，整行是连成一片的白（支路的路面、横臂路面、或者赛道外的空地），`MIDLine_Row_Scan` 的左右游走会一路撞到画面边缘：

- 右转直角 → 右侧扫到 `right = MT9V03X_W-1`；
- 左转直角 → 左侧扫到 `left = 0`。

这两侧在物理上**不是我们的赛道边界**，是"界外"。之前的代码把贴边当成了正常边界，于是：

```
左边界永远 = 0（撞墙）  →  宽度 = 右边界 - 0，比真实宽 1 倍
                     →  midline_info.width 学习值被慢慢污染
                     →  两侧都能取到的行里，(left+right)/2 被 0 拖着往左走
                     →  车往界外那侧打方向
```

再叠加路口策略的"远端主导"权重，车会在直角弯入口就朝拐角打方向——这就是"直角弯转向"。**修法不是调权重，而是先把界外那一侧识别出来、判无效。**

### 17.2 判据（`MIDLine_Row_Scan` 内）

逐行扫描完、拿到这一行的 `left` / `right` 之后：

| 情况 | 判定 | 处理 |
|---|---|---|
| `left` 贴 0、`right` 正常 | 左侧界外（左转直角张开的那一侧） | `out_left[row] = 1`，`left` 作废 |
| `right` 贴 `MT9V03X_W-1`、`left` 正常 | 右侧界外（右转直角张开的那一侧） | `out_right[row] = 1`，`right` 作废 |
| 两侧都贴边 | **路面宽出画面（正常近景）** | 不判界外，维持原样（中线取画面中心） |
| 两侧都不贴边 | 正常 | 不判界外 |

第三行是这条判据的关键：直道近景本来就会两侧撞墙（路比画面宽），如果两侧贴边也判界外，直道会出现一堆"界外行"，反而把中线搞乱。**只有"一侧贴边、另一侧好好的"才是张开的直角。**

### 17.3 界外行在后续每一层的待遇

界外行不是"丢线"，也不是"正常行"，它有自己的待遇，四层各处理一处：

1. **逐行补线（`MIDLine_Edge_Fill`）**：遇到 `out_left[row] || out_right[row]` 直接 `continue`。补线是给丢线用的，界外行补出来的边是"凭空造一条赛道边"，比不补更坏。
2. **加权行循环（`Find_MIDLine`）**：`out_left[row]` 时 `ok_left = 0`、`out_right[row]` 时 `ok_right = 0`。界外侧的列号只是"把下面那条直线往上延长"的产物，落在界外区里没有物理意义，绝不能参与取中点。这一侧直接走单侧逻辑（另一侧 ± 半宽），或者交给直角对补线。
3. **权重（`turn_use`）**：本帧界外行数 `outside_cnt >= MIDLINE_OUTSIDE_MIN_ROWS(4)` → `right_angle = 1` → `turn_use` 强制为 `0`（近景主导），**覆盖掉路口策略的远端主导**。原因很直白：直角弯的远端根本没有我们的赛道，远端权重越高，车越提前按拐角打方向。
4. **十字路口打分**：`real_left/real_right` 快照在补线之前就取了，界外带里那一侧是 `MIDLINE_INVALID_COL`，宽行特征（F1）自然不会误判成"路口张开"。丁字口这类单侧开口靠"宽度快速通道"（§16.2）进入路口状态，再由闸一的 ±8 px 锁航向。

### 17.4 屏显（`y=144` 行加了两组）

| `x=72` / `x=80` | `R` + 直角弯标志 | `1` = 本帧按直角弯处理（近景主导、不提前转向） |

实车看点顺序：进直角弯前 `O` 先涨起来 → `R` 变 1 → 车头保持直行穿过开口 → 出口后 `O` 回落、`R` 回 0、`L` 若短暂非 0 说明出口那几行在补线。

## 18. 第八轮：路口内直行——把"转弯"从控制层掐掉

### 18.1 先说上一轮弄坏了什么（必须承认）

第七轮的"贴边即界外"有一个致命误伤：**直道/弯道上车稍微偏一点，一侧边界就会撞出画面**（赛道宽度 ≈ 30~40 cm，近景只覆盖 ±20 cm 左右）。这时：

```
left == 0（车偏左） → out_left[row] = 1 → ok_left = 0
                   → 本行只剩右侧，中线 = right - 学习半宽
                   → outside_cnt 一旦 >= 4，right_angle = 1
                   → turn_use 被强制 0（近景主导）—— 弯道远端权重被永久关掉
```

结果就是：直道抖、弯道打角变晚变软、整体巡线变差。**根因不是阈值，是判据用错了场合。**

### 18.2 三处收紧

| 位置 | 改法 | 理由 |
|---|---|---|
| `MIDLine_Row_Scan` 界外判据 | 加门控：只有 `cross_hint == 1` 或 `cross_state == INSIDE` 才判界外 | 直道/弯道根本不该走界外逻辑；直角弯会被"宽度快速通道"提前拉进 `cross_hint`，仍然判得到 |
| `right_angle` | 条件加 `&& (1 == cross_hint)` | 双保险，杜绝直道把"近景主导"常态打开 |
| `MIDLINE_CORNER_EN` | `1 → 0`（默认关） | 直角对补基线是四点几何外推，路口里误触发一次就会把中线拽到连线上去；先关，等巡线稳了再单独开 |

### 18.3 真正治"路口转弯"的一刀：控制层直行

前七轮都在改**图像层**，但"车转向"这个动作是**控制层**发出来的。路口里算出来的中线必然是错的（横臂开口、远端错位、直角外推，三种几何都会把它拉向横臂），PID 越是"忠实"地追这条错中线，车越是往横臂里拐。

所以第八轮把这一环直接掐掉，`Control_REMAIN.c` 里取偏差之后立刻：

```c
if(MIDLINE_CROSS_ST_INSIDE == midline_info.cross_state)
{
    error = 0.0f;            // 不追中线 = 不纠偏
}
```

- `error = 0` → 分档打角需求 0° → 舵机回中位 460 → 前轮摆正 → **沿车身方向直行**；
- 车是斜着进路口的也不要紧：零偏差意味着"不做任何修正"，车带着入口那一下的航向穿过去，不会被放大；
- 出路口后（`EXIT` → `COOLDOWN`）自动恢复追线，第一帧抓到的就是对面出口的路，纠偏仍然很快。

配套把 `CONTROL_CROSS_STEER_MAX_DEG` 从 4.5° 收到 **1.5°**：路口内 error 已经是 0，这个限幅退化成兜底，只防纯追踪/差速等旁路塞进大角度。

> 这是"路口内不改航向"的最后一道保险：**不管图像层算出什么鬼中线，路口内舵机都不会大角度转动。** 图像层再怎么调，也突破不了这一层。

### 18.4 一键保守档（`MIDLINE_SAFE_MODE`）

`MIDLine_REMAIN.h` 文件末尾加了总开关：

```c
#define MIDLINE_SAFE_MODE  (1)     // 改成 1 重新编译
```

置 1 时用 `#undef` + `#define` 强制关掉三层高风险几何层：`MIDLINE_FILL_EN`、`MIDLINE_CORNER_EN`、`MIDLINE_OUTSIDE_EN`，只留：

```
逐行扫描 + 加权中线 + 五特征路口判定 + 路口内回中式输出 + 路口内直行(Control)
```

这一档等价于"第一轮 + 第二轮 + 闸一~闸四"，是已知能跑的基线。

**实车排查顺序（一次只开一个，出问题立刻知道是哪一层）：**

## 20. 第二十轮：图像崩坏的真凶——ST7735 窗口偏移，屏幕只放 112×71

### 20.1 真凶：`x2 + 2` 越界

`tft180_show_gray_image()` 内部把区域交给 `tft180_set_region(x1, y1, x2, y2)`，而竖屏分支是带固定偏移写窗口的（`zf_device_tft180.c:171`）：

```c
tft180_write_index(0x2a);           // 列地址
tft180_write_8bit_data(0x00); tft180_write_8bit_data(x1 + 2);
tft180_write_8bit_data(0x00); tft180_write_8bit_data(x2 + 2);
tft180_write_index(0x2b);           // 行地址
tft180_write_8bit_data(0x00); tft180_write_8bit_data(y1 + 1);
tft180_write_8bit_data(0x00); tft180_write_8bit_data(y2 + 1);
```

`x2 = X0 + W - 1`。取 `W = 128、X0 = 0` → `x2 = 127` → **`x2 + 2 = 129`**，而 ST7735 的列地址上限就是 127。多出来的 2 被塞进 8 位寄存器（0x81），控制器认为窗口宽了 2 列，**每写满一行就多吃 2 个像素**，逐行横向累计错位 → 屏幕上就是斜着撕裂的"崩坏"。

这也解释了为什么 `126×80` 一直是好的：`0 + 126 - 1 + 2 = 127`，正好卡在上限。

必守约束（已写成编译期 `#error`）：

```
X0 + W ≤ 126        （列：x2 + 2 ≤ 127）
Y0 + H ≤ 159        （行：y2 + 1 ≤ 159）
```

### 20.2 现在的参数（`Camera_REMAIN.h`）

```c

#define CAMERA_DIS_H   (71)     // 等比：112*120/188 = 71.5
#define CAMERA_DIS_X0  (8)      // 水平居中：(128-112)/2
```

## 21. 第二十一轮：赛道比视野还宽时"没有基线"（裸边线 + 软兜底）

### 21.1 现象与根因

实车在宽白路段（赛道宽度大于摄像头视野）屏幕上没有任何基线/红线，车按自己的方向冲出去。

链路是这样的：

```
最底行整行全白(车压在赛道中央) ──▶ Find_Badpoint 取不到黑→白跳变 ──▶ badpoint_left/right 无效
                              ──▶ bedline_track 没有种子         ──▶ bedline_left/right.valid = 0
                              ──▶ Find_MIDLine 第一分支直接 return ──▶ midline_info.valid = 0
                              ──▶ 控制层走丢线分支(error 按 LOST_DECAY 回中) ──▶ 车头回正 → 冲出去
```

关键认识：**这时的画面不是"看不见赛道"，而是"看得见的全是赛道"**。判丢线（撒手）是最坏的选择。

### 21.2 三层兜底（按可信度排序，`Find_MIDLine` 第一分支内）

| 顺位 | 路径 | 条件 | 输出 | `conf` |
|---|---|---|---|---|
| 1 | `MIDLine_Raw_Output()` | 逐行扫描仍有 ≥`MIDLINE_MIN_ROWS` 行成对边线，且宽度在 `学习宽度×[0.60,1.50]` | 裸边线加权中线（过 `MIDLINE_MAX_JUMP_PX` 限幅） | 40 |
| 2 | `MIDLine_Soft_Output()` | 连裸边线都凑不出（整幅同色） | 沿上一帧中线，每帧只向画面中心靠 3%（`MIDLINE_BLIND_DECAY 0.97`），最长 `MIDLINE_BLIND_MAX`=40 帧（0.8 s） | 25 |
| 3 | `MIDLine_Lost_Output()` | 软兜底超时 | 偏差快速回中（`MIDLINE_LOST_DECAY 0.35`） | 0 |

## 22. 第二十二轮：电机输出降到 50%

### 22.1 改了什么

整条"速度 → 占空比"链路同比例减半，保证前馈斜率不变、闭环自洽：

| 宏 | 原值 | 现值 | 说明 |
|---|---|---|---|
| `CONTROL_BASE_SPEED` | `150.0f` | **`75.0f`** | 闭环目标速度减半 |
| `CONTROL_SPEED_MAX` | `225.0f` | **`112.5f`** | 差速上限跟着降（= 75 × 1.5） |
| `CONTROL_SPEED_MIN` | `45.0f` | **`22.5f`** | 内侧轮下限跟着降（不停转） |
| `CONTROL_DUTY_BASE` | `1200` | **`600`** | 前馈基准占空比减半 |
| `CONTROL_PID_OUT_MAX` | `1000.0f` | **`500.0f`** | 速度环修正量上限跟着收紧 |
| `CONTROL_OVERSPEED_SPEED` | `340.0f` | **`170.0f`** | 超速看门狗门限跟着降，否则降速后再也不会触发 |
| `CONTROL_ENC_FAULT_DUTY` | `1800.0f` | **`900.0f`** | 编码器掉线判据跟着降（巡航占空比 ≈ 842） |

### 22.2 为什么必须成组改

前馈斜率 `control_ff_gain = CONTROL_DUTY_BASE / CONTROL_BASE_SPEED`，改造前后都是 **8.0**：

```
改前：duty = 8.0 × 150 + offset = 1200 + offset   （12% ~ 25% PWM）
改后：duty = 8.0 ×  75 + offset =  600 + offset   （ 6% ~ 17% PWM）
```

只改 `DUTY_BASE` 而不同时改目标速度，闭环会把缺的那部分自己补回来（编码器还读到 150 就一直加占空比），车一点都不会变慢；只改目标速度而不改 `DUTY_BASE`，前馈会过冲再被 PID 拉回来，起步会顿一下。

### 22.3 开环分支也自动跟着半

本地标定没完成 / 编码器故障时走的是开环：

```c
duty_l = (float)CONTROL_DUTY_BASE * (1.0f + ratio) * slow;
duty_r = (float)CONTROL_DUTY_BASE * (1.0f - ratio) * slow;
```

`DUTY_BASE` 减半这里就自动减半，不需要额外改。

### 22.4 还要注意死区

`CONTROL_FF_LEARN_DUTY_MIN` 仍是 `800`（8% 才拖得动带减速箱的车）。它作为固定死区补偿直接加在占空比后面，不参与"减半"：

- 若标定出的死区约 800，则改前 ≈ `1200+800 = 2000`（25%），改后 ≈ `600+800 = 1400`（17.5%）——实际是原来的 **70%**，不是精确 50%；
- 想要更接近 50%：把 `CONTROL_DUTY_BASE` 再降到 450，或者直接把速度规划继续往下调；
- 若车在低速段干脆不动（掉进死区），把 `CONTROL_FF_LEARN_DUTY_MIN` 降到 600 重标一次。
